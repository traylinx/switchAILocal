## What a provider is

A **provider** in switchAILocal is two things joined by a lower-case **provider ID**:

1. An **executor** that knows how to talk to one backend (a CLI binary, a local server, or a cloud API).
2. One or more **credentials** for that executor (an API key from `config.yaml`, an OAuth token file in `auth-dir`, or an implicit "local" credential).

The provider ID is what you write before the colon in `ollama:llama3.2`, what you put in a virtual model member's `provider:` field, and what appears in logs and in `GET /v1/providers`.

## Provider families at a glance

| Provider ID | Backend | How it is enabled | Colon prefix | Where its model list comes from |
|-------------|---------|-------------------|--------------|---------------------------------|
| `geminicli` | Google Gemini CLI (`gemini` binary) or Gemini OAuth (Code Assist API) | `gemini` on `PATH`, or `--login` | `geminicli:` | Model list fetched from the public Gemini CLI repository |
| `claudecli` | Claude Code CLI (`claude` binary) | `claude` on `PATH` | `claudecli:` | Built-in static list |
| `codex` | OpenAI Codex CLI (`codex` binary), Codex OAuth, or `codex-api-key` | `codex` on `PATH`, `--codex-login`, or config | `codex:` | Built-in static list (CLI), your `models:` (API key) |
| `vibecli` | Mistral Vibe CLI (`vibe` binary) | `vibe` on `PATH` | `vibecli:` | Built-in static list |
| `ollama` | Ollama server | `ollama.enabled: true` | `ollama:` | `GET /api/tags` when `auto-discover: true` |
| `lmstudio` | LM Studio server | `lmstudio.enabled: true` | none | Not discovered (reach it through a [virtual model](/advanced/virtual-models)) |
| `opencode` | OpenCode server (agents) | `opencode.enabled: true` | `opencode:` | `GET /agent` on the OpenCode server |
| `gemini` | Google Gemini API (AI Studio key) | `gemini-api-key` | `gemini:` | Your `models:` list |
| `claude` | Anthropic Messages API | `claude-api-key` | `claude:` | Your `models:` list |
| `switchai` | Hosted switchAI endpoint | `switchai-api-key` | `switchai:` | Your `models:` list, plus `models-url` |
| `vertex` | Vertex AI (service account) or Vertex-style API-key gateways | `--vertex-import`, or `vertex-api-key` | none | Built-in Gemini list, or your `models:` |
| `<name>` | Any OpenAI-compatible API (Groq, OpenRouter, DeepSeek, MiniMax, Kimi, Alibaba DashScope, ...) | `openai-compatibility` entry | only `openai:` / `openai-compat:` names | Your `models:` list, plus `models-url` |
| `antigravity` | Antigravity (Google OAuth) | `--antigravity-login` | none | Fetched from the upstream after login |
| `qwen` | Qwen portal (OAuth) | `--qwen-login` | none | None registered in this release |
| `iflow` | iFlow (OAuth or cookie) | `--iflow-login`, `--iflow-cookie` | none | None registered in this release |
| `aistudio` | Google AI Studio via the WebSocket relay | a relay client connected to `/v1/ws` with a channel ID starting `aistudio-` | none | None registered in this release |

"Colon prefix" means `provider:model` is parsed as an explicit provider pin. Only these prefixes are recognized (`internal/util/provider.go`): `switchai`, `gemini`, `geminicli`, `claude`, `claudecli`, `codex`, `ollama`, `vibecli`, `openai`, `openai-compat`, `opencode`. Any other `xxx:yyy` string is treated as an ordinary model name. See [Routing](/concepts/routing) for the full resolution order.

<Note>
Detailed, copy-paste setup for each family is in the [Provider Setup Guide](/guides/setup-providers).
</Note>

## CLI providers (local binaries)

At startup switchAILocal scans `PATH` for four binaries (`internal/cli/discovery.go`) and registers each one it finds as a provider. No configuration is needed.

| Binary | Provider ID | Invocation | Streams | `@` attachments | Model forwarded |
|--------|-------------|------------|---------|-----------------|-----------------|
| `gemini` | `geminicli` | prompt on stdin, `--output-format=json` / `stream-json` | yes | yes | yes, as `--model=<name>` |
| `claude` | `claudecli` | `--print`, `--output-format=json` / `stream-json` | yes | no | no (CLI default) |
| `codex` | `codex` | `-p <prompt>` | no (buffered) | no | no (CLI default) |
| `vibe` | `vibecli` | `-p <prompt>` | no (buffered) | yes | no (CLI default) |

Behaviour worth knowing:

- Requests run as a subprocess per call, using your existing CLI login and subscription.
- `claude` gets `--dangerously-skip-permissions` automatically when there is no TTY; `gemini` always gets `-y` and `--include-directories` scoped to a sandbox (or the [billboard](#billboard) directory).
- Per-request CLI options (attachments, sandbox/auto-approve flags, session resume) are passed in `extra_body.cli`; see [CLI Attachments](/api/cli-attachments).
- If `REMOTE_COMMAND_HOST` is set, CLI calls are forwarded to a `bridge-agent` instance instead of being run locally (the bridge only runs `gemini`, `claude`, `vibe`, `codex` and requires `BRIDGE_AGENT_SECRET`).

<Warning>
A CLI provider and an HTTP credential share the provider ID. If you also have an OAuth login file or an API key that maps to `geminicli` or `codex`, the HTTP executor for that credential takes over the provider ID and the CLI binary is no longer used. Use one or the other per provider ID.
</Warning>

## Local server providers

### Ollama

```yaml
ollama:
  enabled: true
  base-url: "http://localhost:11434"   # default
  auto-discover: true                  # register models from /api/tags
```

Chat goes to Ollama's native `/api/chat` (translated to and from OpenAI format, including images and streaming); embeddings go to `/v1/embeddings`. Because Ollama is a trusted local provider, `ollama:<any-model>` is forwarded even when the model was not discovered.

### LM Studio

```yaml
lmstudio:
  enabled: true
  base-url: "http://localhost:1234/v1"  # default
```

Requests are forwarded unchanged to `<base-url>/chat/completions` (the body, including the client's `model` value, is not rewritten). LM Studio models are **not** auto-discovered in this release and `lmstudio:` is not a recognized prefix, so route to it through a virtual model whose ID equals the LM Studio model ID, with one member `provider: lmstudio`. The `auto-discover`, `models`, `models-url` and `headers` keys are accepted but not used.

### OpenCode

```yaml
opencode:
  enabled: true
  base-url: "http://localhost:4096"  # default
  default-agent: "build"
```

OpenCode agents (from `GET /agent`) are registered as model IDs, and `opencode:<agent>` routes to the OpenCode server. Each request opens an OpenCode session and sends only the **last user message**; earlier messages are not replayed. To continue a conversation, send the same `session_id` (top level or in `extra_body.session_id`) and switchAILocal reuses the mapped OpenCode session. The agent name and `default-agent` are not forwarded in this release, so OpenCode answers with its own configured agent.

## Cloud API-key providers

All of these live in `config.yaml`, support several entries (keys) per provider, and accept `prefix`, `proxy-url`, `headers` and `models` (all but `vertex-api-key` also accept `excluded-models`). `models-url` adds discovered models for `switchai-api-key`; on `gemini-api-key` / `claude-api-key` it is only used by the auto-routing probe.

<Warning>
`gemini-api-key`, `claude-api-key` and `codex-api-key` ship **no default model list** in this release. Only models you list under `models:` are registered for that key. A key with no `models:` loads but cannot serve requests (`no active credentials found for provider ...`).
</Warning>

| Block | Provider ID | Default upstream | Notes |
|-------|-------------|------------------|-------|
| `gemini-api-key` | `gemini` | `https://generativelanguage.googleapis.com` | Native Gemini protocol; duplicates of the same key are dropped. |
| `claude-api-key` | `claude` | `https://api.anthropic.com` | Native Messages API. |
| `codex-api-key` | `codex` | none in config (OAuth tokens use the ChatGPT Codex backend) | `base-url` is **required**; entries without it are dropped. Requests go to `<base-url>/responses`. |
| `switchai-api-key` | `switchai` | `https://switchai.traylinx.com/v1` | OpenAI-compatible. |
| `vertex-api-key` | `vertex` | none | `base-url` required; the executor appends `/v1/publishers/google/models/{model}:{action}` and sends the key as `x-goog-api-key`. |

### OpenAI-compatible providers

Any service that speaks the OpenAI REST API is added as an `openai-compatibility` entry. The entry's `name` (lower-cased) becomes the provider ID.

```yaml
openai-compatibility:
  - name: "deepseek"
    base-url: "https://api.deepseek.com/v1"     # required; entries without it are dropped
    models-url: "https://api.deepseek.com/v1/models"  # optional discovery
    api-key-entries:
      - api-key: "sk-your-deepseek-key"
    models:
      - name: "deepseek-v4-pro"        # upstream model name
        alias: "deepseek-pro"          # public ID clients send
        context_length: 1000000        # shown in /v1/models
```

Per-model options: `alias`, `expose: false` / `visibility: private` (routable but hidden from `/v1/models`), `context_length`, `capabilities` (same shape as [virtual model capabilities](/advanced/virtual-models#capabilities), advertised in `/v1/models`), and `native_tools` (provider-native tools such as MiniMax `web_search`, advertised so agent clients can opt in).

Per-entry options: `prefix`, `headers` (for example a custom `User-Agent`), `proxy-url`, `excluded-models`, and `kimi-history-shim` (default `true`: inserts a placeholder `reasoning_content` on replayed assistant tool-call messages, which thinking-mode Kimi and DeepSeek endpoints require; harmless elsewhere).

The OpenAI-compatible executor serves chat, completions, Responses, embeddings, image generation and edits, audio transcription/translation/speech, and music/lyrics. MiniMax speech and music requests go through dedicated adapters; see [Media Generation](/advanced/media).

## OAuth and login-based providers

Logins run once from the command line and write a token file into `auth-dir` (default `~/.switchailocal`). Tokens are refreshed automatically.

| Flag | Provider ID | Token file | Needs env vars |
|------|-------------|------------|----------------|
| `--login` (Gemini / Code Assist) | `geminicli` | `<email>-<project>.json` | `GEMINI_CLIENT_ID`, `GEMINI_CLIENT_SECRET` |
| `--codex-login` | `codex` | `codex-<email>.json` | none |
| `--claude-login` | `claudecli` | `claude-<email>.json` | none |
| `--qwen-login` | `qwen` | `qwen-<email>.json` | `QWEN_CLIENT_ID` |
| `--iflow-login` / `--iflow-cookie` | `iflow` | `iflow-<email>-<ts>.json` | `IFLOW_CLIENT_ID`, `IFLOW_CLIENT_SECRET` (OAuth only) |
| `--antigravity-login` | `antigravity` | `antigravity-<email>.json` | `ANTIGRAVITY_CLIENT_ID`, `ANTIGRAVITY_CLIENT_SECRET` |
| `--vertex-import <key.json>` | `vertex` | service-account credential | none |

<Warning>
Known limitations in this release (from reading the code; verify on your build):
- `--claude-login` tokens are loaded under the `claudecli` ID, which only has a CLI executor. Use the `claude` binary or a `claude-api-key` instead.
- Login credentials only serve models registered *for that credential*. `--codex-login`, `--qwen-login`, `--iflow-login` and the AI Studio relay register none, so requests cannot be routed to them. `--login` (Gemini) registers the discovered Gemini CLI list once the discovery cache is filled (after the first background discovery run; restart if it is empty). `--antigravity-login` fetches its list from the upstream.
- `--vibe-login` and `--ollama-login` only write a placeholder file. Vibe is enabled by `PATH` detection; Ollama by the `ollama:` config block.
</Warning>

See [Authentication](/concepts/authentication) for callback ports, headless login and token storage backends.

## How models become routable

A model ID is routable when some credential has registered it in the model registry:

- **Config lists:** each `models:` entry registers its `alias` (or `name` if no alias).
- **Discovery:** at startup a background job fetches the Gemini CLI model list, Ollama `/api/tags`, OpenCode `/agent`, and every `models-url`, and adds static lists for `claudecli`, `codex` and `vibecli`. Results are cached in `<auth-dir>/cache/discovery`. Re-run it with `POST /v1/models/refresh` (optionally `?provider=<id>`).
- **Prefixes:** a credential with `prefix: team-a` also registers `team-a/<model>` for each of its models. Those prefixed IDs are hidden from `/v1/models` unless `force-model-prefix: true`, in which case *only* prefixed IDs are registered.
- **Exclusions:** `excluded-models` (per key) and `oauth-excluded-models` (per provider ID, for OAuth/file credentials) remove matching IDs. Patterns are case-insensitive and support `*` wildcards.

Use `GET /v1/models` to see the public catalog and `GET /v1/providers?filter=active` to see which provider IDs have models registered.

## Billboard

```yaml
billboard:
  enabled: true
  base-dir: "~/.switchailocal/billboard"
```

When enabled, CLI providers receive a system note telling the model to use this folder for file operations when no path is given, and `gemini` gets it as its `--include-directories` workspace.

## Proxies

```yaml
proxy-url: "socks5://user:pass@127.0.0.1:1080/"   # global
gemini-api-key:
  - api-key: "your-gemini-key"
    proxy-url: "http://proxy.internal:8080"        # per credential
```

Supported schemes: `http`, `https`, `socks5`. `openai-compatibility` also accepts `proxy-url` per entry and per `api-key-entries` item.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Provider 'gemini' is not active (503)">
    The `gemini:` prefix was used but no Gemini API key has registered models. Add a `models:` list to the `gemini-api-key` entry. The same applies to `claude:` and `codex:` with API keys.
  </Accordion>
  <Accordion title="no active credentials found for provider 'x'">
    A credential exists but does not list the requested model. Add the model under that credential's `models:` (or enable `models-url`), or check `excluded-models`.
  </Accordion>
  <Accordion title="A CLI provider is not detected">
    The binary must be on the `PATH` of the switchAILocal process (services and launch agents often have a reduced `PATH`). Run with `debug: true` and look for `Discovered local CLI tool` / `Local CLI tool not found`.
  </Accordion>
  <Accordion title="lmstudio:my-model returns model not found">
    `lmstudio` is not a recognized colon prefix. Create a virtual model named like the LM Studio model, with a member `provider: lmstudio`.
  </Accordion>
  <Accordion title="Kimi or DeepSeek returns 400 about reasoning_content">
    Keep `kimi-history-shim` enabled (the default) on that `openai-compatibility` entry.
  </Accordion>
</AccordionGroup>
