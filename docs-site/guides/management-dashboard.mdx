The management dashboard is a single-page web app served by the gateway at
`/management`. It edits `config.yaml` through the
[Management API](/api/management/overview), so every change it makes is also
possible with `curl`.

```text
http://localhost:18080/management
```

## What it can do

| Section | Functions |
| ------- | --------- |
| **Providers** | Add, edit and remove provider entries (API keys, OpenAI-compatible services, local servers), test a connection, discover a provider's models |
| **Routing** | Auto-routing status and decision journal; Amp model mappings |
| **Settings** | Global `proxy-url`, debug mode, read-only view of host, port and TLS |

Saving a provider or a setting sends the whole configuration back with
`PUT /v0/management/config.yaml`; Amp model mappings use their own endpoint.

<Warning>
  Known issue in 0.6.2: saves from the Providers and Settings sections fail with
  `400 invalid_yaml ... cannot unmarshal !!int ... into time.Duration`, because
  the dashboard sends the JSON form of the config (where durations are
  numbers) to an endpoint that expects YAML. The file is left unchanged. Until
  this is fixed, edit `config.yaml` directly (it reloads live) or use the
  per-field endpoints of the [Management API](/api/management/overview).
  Testing providers, model discovery and the Routing section are not affected.
</Warning>

## Where the page comes from

The server serves the file `management.html` from the first location that
applies:

1. `MANAGEMENT_STATIC_PATH` (a folder, or the full path to the file);
2. `$WRITABLE_PATH/static/`;
3. a `static/` folder next to the active `config.yaml`.

| Install type | File present? |
| ------------ | ------------- |
| Docker image | Yes, `/app/static/management.html` |
| Source checkout, config in the repo root | Yes, `static/management.html` |
| Release archive | No. Download it into `static/` next to `config.yaml` ([how](/installation#release-archive)) |

If the file is missing, `/management` returns `404` and the server tries to
download a newer copy in the background from the GitHub releases of
`remote-management.panel-github-repository`. It checks again at most every
3 hours. As of 0.6.2 the default repository offers no public release to
download from, so in practice the bundled or manually placed file is what you
get, and the log shows `failed to fetch latest management release information`.

`remote-management.disable-control-panel: true` turns off both the page and the
background download. The API keeps working.

## First visit

The page first calls `GET /v0/management/setup-status`:

| Config | What you see |
| ------ | ------------ |
| No `secret-key`, no `MANAGEMENT_PASSWORD` | The dashboard opens without a login (localhost only) |
| `secret-key: disabled` | Opens without a login from localhost |
| A secret is set | Login screen; enter the plaintext secret |

In 0.6.2 `setup-status` always reports the server as configured, so the
dashboard's first-run "set password / skip" screen does not appear. The same
actions are available as localhost-only API calls:

```bash
# Set the first management secret. Also sets allow-remote: true.
curl -X POST http://localhost:18080/v0/management/initialize \
  -H "Content-Type: application/json" -d '{"secret": "a-long-random-secret"}'

# Or: no password for localhost (secret-key: disabled, allow-remote: false)
curl -X POST http://localhost:18080/v0/management/skip
```

After `initialize`, set `allow-remote: false` in `config.yaml` if you only use
the dashboard locally.

The browser keeps the secret in `localStorage` (`switchai_management_key`) and
sends it as `Authorization: Bearer <secret>`. A `401` clears it and shows the
login again.

## Set a secret in the config instead

```yaml config.yaml
remote-management:
  allow-remote: false          # true to manage from other machines
  secret-key: "a-long-random-secret"
```

The plaintext is replaced with its bcrypt hash at the next start. To change it,
write a new plaintext value and restart. `MANAGEMENT_PASSWORD` in the
environment works as an additional accepted secret.

## Using it from another machine or from Docker

Requests that are not direct loopback connections are remote. That includes
browsers on other machines, requests through a reverse proxy (any
`X-Forwarded-For`, `X-Real-IP` or `Forwarded` header), and requests from the
host into a Docker container through a published port. Remote access needs:

```yaml config.yaml
remote-management:
  allow-remote: true
  secret-key: "a-long-random-secret"
```

Use TLS or a VPN for anything beyond a trusted LAN. Five wrong secrets ban a
remote IP for 30 minutes.

## Rebuild the dashboard

The source is in `frontend/` (React, built with Vite into one HTML file).

```bash
cd frontend && npm install && cd ..
./ail_ui.sh      # npm run build → static/management.html
```

## Useful API calls

The dashboard is a thin client; for scripts call the API directly
(`X-Management-Key` or `Authorization: Bearer`):

```bash
KEY="a-long-random-secret"
curl -H "X-Management-Key: $KEY" http://localhost:18080/v0/management/config
curl -H "X-Management-Key: $KEY" http://localhost:18080/v0/management/config.yaml
curl -H "X-Management-Key: $KEY" http://localhost:18080/v0/management/heartbeat/status
curl -H "X-Management-Key: $KEY" http://localhost:18080/v0/management/usage
curl -X PUT -H "X-Management-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"value": true}' http://localhost:18080/v0/management/debug
```

Full list: [Management API](/api/management/overview).

## Troubleshooting

<AccordionGroup>
  <Accordion title="/management returns 404">
    The `management.html` file is not where the server looks (see
    [Where the page comes from](#where-the-page-comes-from)), or
    `disable-control-panel` is `true`. Place the file in `static/` next to
    `config.yaml`, or set `MANAGEMENT_STATIC_PATH`.
  </Accordion>
  <Accordion title="403 remote management disabled">
    Your browser is not a direct loopback client (other machine, reverse
    proxy, or Docker port mapping). Set `allow-remote: true` with a secret.
  </Accordion>
  <Accordion title="401 invalid management key">
    Use the plaintext secret, not the `$2a$...` hash from `config.yaml`. Clear
    the stored key by logging out or clearing site data.
  </Accordion>
  <Accordion title="Saving fails">
    `400 invalid_yaml ... time.Duration` is the 0.6.2 known issue above; edit
    `config.yaml` instead. Otherwise the server must be able to write
    `config.yaml` (in Docker: UID `100`), and a `422 invalid_config` response
    contains the validation error.
  </Accordion>
  <Accordion title="Forgot the secret">
    From the same machine, use **Reset Configuration (Localhost Only)** on the
    login screen, or `curl -X POST http://localhost:18080/v0/management/reset`.
    Both clear the secret (management becomes open to localhost) and set
    `allow-remote: false`. Or write a new plaintext `secret-key` into
    `config.yaml` and restart.
  </Accordion>
</AccordionGroup>
