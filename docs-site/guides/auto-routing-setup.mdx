## What it is

The **auto-routing engine** (`internal/autoroute`, config block `auto-routing:`) handles requests whose `model` is `auto`, `auto:<intent>`, `cortex`, or empty. It:

1. Probes your providers at startup to build a candidate list (provider + model).
2. Estimates prompt complexity and classifies intent with fast keyword heuristics (no LLM call).
3. Optionally narrows candidates with an `intent-matrix`, and removes `disabled-providers`.
4. Scores every candidate and returns the winner plus the remaining available candidates as fallbacks.
5. Learns from outcomes: latency, success rate and rate-limit headers feed back into the scores.

It is separate from the Lua [Cortex Router](/intelligent-systems/cortex-router) plugin and the `intelligence:` block. If the Lua plugin is enabled it runs first and can rewrite `auto` before this engine sees it.

## When to use it

- You have several working providers and want cheap, healthy ones picked automatically for simple prompts.
- You want requests to move away from a provider that starts failing or rate limiting.
- You want simple intent hints (`auto:coding`) without maintaining a classifier model.

If you want a fixed set of backends with exact ratios, use [Virtual Models](/advanced/virtual-models) instead.

## Minimal working config

```yaml config.yaml
auto-routing:
  enabled: true
```

Everything else has defaults. Restart the server; the log shows `Initializing Intelligent Auto-Routing System`, one `Discovered provider models` line per reachable provider, and `Intelligent Auto-Routing Ready` with the candidate count.

## Example request

```bash
curl -i http://localhost:18080/v1/chat/completions \
  -H "Authorization: Bearer sk-test-123" \
  -H "Content-Type: application/json" \
  -d '{"model": "auto:coding", "messages": [{"role": "user", "content": "Write a binary search in Go"}]}'
```

The response carries:

```text
X-Auto-Routed: true
X-Selected-Model: <winning candidate model ID>
X-Selected-Provider: <text before the first ":" of that ID, or the whole ID>
```

## How candidates are found

Candidates come from boot-time probes only (`internal/api/server.go`):

| Source | Probe | Candidate provider ID |
|--------|-------|-----------------------|
| `gemini`, `claude`, `codex` binaries | `<binary> --version` (and `claude account` for a tier hint) | `geminicli`, `claudecli`, `codex` |
| each `gemini-api-key` entry | `GET <base-url>/v1beta/models` (or `models-url`) | `gemini-api-<n>` |
| each `claude-api-key` entry | `GET <base-url>/v1/models` (or `models-url`) | `claude-api-<n>` |
| `ollama.enabled: true` | `GET <base-url>/api/tags` | `ollama` |

Models are taken from the probe response. CLI probes return no model list, so CLIs only contribute candidates when `probe-on-startup: false`, in which case a fixed fallback set is used instead of probing: `geminicli`, `claudecli`, `codex`, `ollama`, each with model `auto`.

<Warning>
Known limitations in this release:
- `openai-compatibility`, `switchai`, LM Studio, OpenCode and virtual models are **not** probed, so they never become auto-routing candidates.
- API-key probes register under synthetic provider IDs (`gemini-api-0`, `claude-api-0`) that have no executor. If one of them wins, that attempt fails with `executor not registered` and the request moves to the next provider. Use `disabled-providers: [gemini-api-0, claude-api-0]` or rely on Ollama/CLI candidates.
- The winner's provider is derived from its model ID (text before the first `:`). Probe-discovered IDs such as `llama3.2` carry no provider prefix, so the first attempt targets a non-existent provider and the request is actually served by the next candidate's provider. This works when that provider also has the model (for example two Ollama candidates); `X-Selected-Provider` shows the derived value, not the provider that answered.
- The fallback chain is a list of providers, but every attempt sends the **winner's** model name. A fallback provider that does not serve that model fails with `no active credentials found`.
- The Gemini API-key probe sends the key as a Bearer token and expects an OpenAI-style `data` list, so against the official Gemini API it reports no models.
- `probe-interval` and `passive-monitoring` are accepted but not used; there is no periodic re-probing. Restart to rediscover.
</Warning>

## How a candidate is scored

```text
base   = w.availability × available(0|1)
       + w.quota        × quota_health(0..1)
       + w.latency      × latency_score   (0 ms → 1.0, ≥5000 ms → 0.0, unknown → 0.5)
       + w.success-rate × success_rate    (unknown → 0.7)
final  = (base + tier_boost + preference × 0.20) × conservation_multiplier
```

- **Tier boost:** `premium` +0.30, `standard` +0.15, `local` +0.05, `free` 0, `reserve` −0.10. Tiers come from `auto-routing.providers.<id>.tier` / `model-tiers`, otherwise from the provider name: IDs ending in `cli` → standard, `gemini`/`claude`/`codex` → standard, `lmstudio` → local, everything else (including `ollama`) → free.
- **Preference:** an exact match on the candidate's model ID adds `preference × 0.20`.
- **Conservation:** complexity is estimated from request size (`len/4` tokens bucketed to 0.1–0.9). If complexity is below `simple-threshold-tokens / 1000`, premium tiers get ×0.3 and free/local tiers ×1.5; above 0.7, premium gets ×1.2.
- Ties go to lower latency, then alphabetical model ID.

### Intent classification

`auto:<hint>` sets the intent directly. Hints are normalized: `code`/`programming`/`dev` → `coding`, `think`/`math`/`logic` → `reasoning`, `write`/`story`/`poem` → `creative`, `quick`/`simple`/`chat` → `fast`, `image`/`screenshot` → `vision`, `private`/`local`/`sensitive` → `secure`; unknown hints pass through unchanged. Without a hint, keyword heuristics pick `vision`, `secure`, `coding`, `reasoning`, `creative`, `fast`, or `general`.

The intent only matters if you define an `intent-matrix`. Candidates whose model ID appears in the matching list are kept; if none match, all candidates stay.

## Learning from traffic

After each auto-routed request the outcome updates per-provider health: latency (moving average), success rate, and quota health from rate-limit headers (`anthropic-ratelimit-*`, `x-ratelimit-*`). Three consecutive failures mark a provider degraded; ten (or a single 429) mark it unavailable and start a cooldown of 5 s doubling up to 5 min (±10% jitter). A background loop clears expired cooldowns every 60 s.

With `lab.enabled: true`, a shadow experiment evaluates alternative weights, keeps or discards them per `adaptation-interval`, and journals decisions to `logs/autoroute/experiments.tsv` next to your config file.

## Configuration reference

```yaml config.yaml
auto-routing:
  enabled: true                 # default false
  max-resolution-ms: 5ms        # scoring time budget; Go duration
  weights:                      # must sum to 1.0, otherwise all four are reset to the defaults below
    availability: 0.35
    quota: 0.25
    latency: 0.20
    success-rate: 0.20
  preferences:
    - model: "llama3.2"         # matches the candidate model ID exactly
      preference: 0.9           # 0.0 – 1.0
      reason: "local first"
  providers:
    ollama:
      tier: local               # premium | standard | free | local | reserve
      model-tiers:
        "qwen3:32b": standard
  intent-matrix:
    coding: ["qwen3-coder:30b", "gemini-2.5-pro"]
  disabled-providers: ["gemini-api-0"]   # never selected; no auto-recovery
  discovery:
    enabled: true               # must be true or no probes run
    probe-on-startup: true
    probe-timeout: 5s
    cache-ttl: 24h
  conservation:
    enabled: true
    simple-threshold-tokens: 500
  lab:
    enabled: false
    adaptation-interval: 24h
    max-weight-drift: 0.10
    min-observation-window: 10
```

| Key | Default | Notes |
|-----|---------|-------|
| `enabled` | `false` | Master switch. |
| `max-resolution-ms` | `5ms` | If scoring exceeds it, the request falls back to legacy auto resolution. |
| `discovery.enabled` | `false` if omitted | Required for probing. The example config sets it to `true`. |
| `discovery.probe-timeout` | `5s` | Total probe budget (boot discovery is also capped at 10 s). |
| `conservation.premium-conservation-at` | `0.20` | Accepted; not used by the scorer in this release. |
| `providers.<id>.monthly-budget` | — | Accepted; not used. |

### Legacy priority list

```yaml
routing:
  auto-model-priority: ["llama3.2", "gemini-2.5-flash"]
```

On load this list is converted into `auto-routing.preferences` (0.9, 0.8, ... down to 0.1) and removed from the file. If auto-routing is disabled or fails, `auto` resolves to the first available model in this list, else to the newest registered model.

## Observability

```bash
# Lab status (requires lab.enabled; otherwise {"enabled": false})
curl -H "X-Management-Key: $MGMT_KEY" http://localhost:18080/v0/management/autoroute/status

# Last N decisions from the lab journal (1–100, default 50)
curl -H "X-Management-Key: $MGMT_KEY" "http://localhost:18080/v0/management/autoroute/journal?limit=20"
```

Both return `503 auto-routing not initialized` when `auto-routing.enabled` is false. With `observability.metrics.enabled: true`, provider health is exported as the `switchailocal_provider_health_score` Prometheus gauge on `/metrics`.

## Troubleshooting

<AccordionGroup>
  <Accordion title="No X-Auto-Routed header">
    Auto-routing did not handle the request. Check that `auto-routing.enabled` and `auto-routing.discovery.enabled` are true, that the startup log reports a non-zero candidate count, and that no Lua plugin rewrote `auto` first.
  </Accordion>
  <Accordion title="Intelligent Auto-Routing Ready with candidates=0">
    No probe returned models. Probes cover only Gemini/Claude API keys and Ollama; make sure Ollama is running, or set `probe-on-startup: false` to use the fixed CLI fallback set.
  </Accordion>
  <Accordion title="executor not registered for provider gemini-api-0">
    A synthetic API-key probe ID won and no fallback succeeded. Add it to `disabled-providers`.
  </Accordion>
  <Accordion title="Weights seem ignored">
    Weights that do not sum to 1.0 (±0.01) are silently replaced with the defaults.
  </Accordion>
</AccordionGroup>
