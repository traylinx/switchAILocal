The Management API reads and changes a running server: configuration, client keys, provider credentials, logs, usage, and OAuth logins. The bundled control panel (`/management`) is a client of this API.

```text
http://localhost:18080/v0/management
```

<Warning>
**Do not expose `/v0/management` to the internet.** It can read every provider key in clear text (`GET /config`, `GET /config.yaml`, the key-list endpoints), rewrite the config file, and upload credentials. Keep `remote-management.allow-remote: false` (the default), bind the server to `127.0.0.1`, or block `/v0/management` at your reverse proxy. Remote access is meant for trusted LAN or VPN admin use only.
</Warning>

## Authentication

Management routes use their own key. Client API keys from `api-keys` are **not** accepted.

### Configuring the key

```yaml config.yaml
remote-management:
  allow-remote: false     # allow non-loopback clients
  secret-key: ""          # plaintext here is bcrypt-hashed and written back on startup
  disable-control-panel: false
```

You can also set the `MANAGEMENT_PASSWORD` environment variable. It is compared in plaintext, and it **also turns on remote access** regardless of `allow-remote`.

The standalone server's `--password` flag sets a runtime-only local password, accepted only from localhost.

### Sending the key

```bash
curl http://localhost:18080/v0/management/config -H "Authorization: Bearer YOUR_MANAGEMENT_KEY"
curl http://localhost:18080/v0/management/config -H "X-Management-Key: YOUR_MANAGEMENT_KEY"
```

### How a request is decided

"Localhost" means the TCP peer is a loopback address **and** the request has no `X-Forwarded-For`, `X-Real-IP`, or `Forwarded` header. Requests through a local reverse proxy therefore count as remote. Rows are checked top to bottom; the first match decides.

| Situation | Localhost client | Remote client |
|---|---|---|
| Remote client and remote access off (`allow-remote: false`, no `MANAGEMENT_PASSWORD`) | n/a | `403 {"error":"remote management disabled"}` |
| No `secret-key` and no `MANAGEMENT_PASSWORD` | **allowed without a key** (`X-Management-Auth: bypass`) | Server refuses to start if `allow-remote: true` |
| `secret-key: "disabled"` (set by `POST /skip`) | allowed without a key (`X-Management-Auth: localhost-bypass`) | key required, and nothing matches, so always `401` |
| A key is configured | key required | key required |

When a key is required:

| Status | Body |
|---|---|
| `401` | `{"error":"missing management key"}` |
| `401` | `{"error":"invalid management key"}` |
| `403` | `{"error":"IP banned due to too many failed attempts. Try again in <duration>"}`: 5 failed attempts from one remote IP block it for 30 minutes (localhost is never banned) |

Every response from routes behind this check carries `X-CPA-VERSION`, `X-CPA-COMMIT`, and `X-CPA-BUILD-DATE`.

Management routes also go through the global CORS middleware (`Access-Control-Allow-Origin: *`). Browser pages on other origins can call them if they know the key, which is one more reason to keep them local.

## First-run setup

These four routes are registered **before** the auth middleware, so they need no key. The three that change state only work from localhost.

### GET /setup-status

```json
{"isConfigured": true, "authDisabled": false}
```

`authDisabled` is `true` when no key is configured, or when the key is `disabled` and the caller is on localhost. In the current code `isConfigured` is always `true`.

### POST /initialize

Sets the first management key.

```bash
curl -X POST http://localhost:18080/v0/management/initialize \
  -H "Content-Type: application/json" \
  -d '{"secret": "YOUR_NEW_MANAGEMENT_KEY"}'
```

- Stores the bcrypt hash in `remote-management.secret-key` **and sets `allow-remote: true`**. Set it back to `false` if you only manage locally.
- Returns `200 {"status":"ok","message":"management secret initialized successfully"}`.
- `400` when `secret` is missing.
- `403` from a non-localhost client, or when a key already exists (in config or env).

### POST /skip

No body. Sets `secret-key: "disabled"` and `allow-remote: false`: keyless access from localhost only. This overwrites an existing key. Returns `{"status":"ok","message":"auth disabled for localhost"}`, or `403` from a remote client.

### POST /reset

No body. Clears `secret-key` and sets `allow-remote: false`. Returns `{"status":"ok","message":"configuration reset"}`, or `403` from a remote client.

## Conventions

- Bodies and responses are JSON unless noted.
- Requests that change configuration write `config.yaml` (comments preserved) and respond `{"status":"ok"}`. A write failure returns `500 {"error":"failed to save config: ..."}`.
- Simple settings take `{"value": <bool|int|string>}`. PUT and PATCH behave the same on them.
- Changes take effect immediately (hot reload).
