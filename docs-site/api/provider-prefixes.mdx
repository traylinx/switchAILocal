Every inference route (`/v1/chat/completions`, `/v1/completions`, `/v1/responses`, `/v1/messages`, `/v1beta/models/...`, `/v1/embeddings`, images, audio, music) resolves the `model` value the same way, in this order:

1. **Explicit `provider:model` prefix**, if the part before the first `:` is a recognized provider prefix.
2. **Lua plugin hook** (`on_request`), if plugins are enabled. It may rewrite the model or pick providers.
3. **Virtual model** (`virtual-models:` in config, for example `ail-compound`).
4. **Auto-routing**, for `auto`, `auto:<intent>`, `cortex`, or an empty model. See [Auto-Routing](/api/auto-routing).
5. **Registry lookup**: every provider that registered that exact model ID (including aliases) is a candidate.

If nothing matches: `400 unknown provider for model <id>`.

## Explicit prefixes

Syntax: `<prefix>:<model>`. The prefix is case-insensitive. Only these prefixes are recognized:

| Prefix | Provider | Requirement |
|---|---|---|
| `geminicli` | Gemini CLI (`gemini` binary on `PATH`) | none checked up front |
| `claudecli` | Claude Code CLI (`claude`) | none checked up front |
| `vibecli` | Mistral Vibe CLI (`vibe`) | none checked up front |
| `ollama` | Ollama (`ollama.base-url`) | none checked up front |
| `opencode` | OpenCode server (`opencode.base-url`) | none checked up front |
| `codex` | OpenAI Codex (CLI or `codex-api-key`) | provider must be active |
| `gemini` | Gemini API (`gemini-api-key`) | provider must be active |
| `claude` | Anthropic API (`claude-api-key`) | provider must be active |
| `switchai` | `switchai-api-key` entries | provider must be active |
| `openai` | A provider registered under the ID `openai` | provider must be active |
| `openai-compat` | A provider registered under the ID `openai-compat` | provider must be active |

"Active" means the provider currently has registered models (see [`GET /v1/providers`](/api/models#get-v1providers)). The model part is passed to that provider with the prefix removed. An empty model part (`ollama:`) becomes `auto`.

<Warning>
`vibe:`, `lmstudio:`, `groq:`, `minimax:`, and other names are **not** prefixes. A value such as `groq:gpt-oss-20b` is looked up as a whole model ID, so it only works if you configured that exact string as an alias (see below).
</Warning>

If a prefix that must be active is not, the request fails with `503 Provider '<x>' is not active. Please configure it in config.yaml or use --login flags.` Unrecognized prefixes never error at this step; they are simply treated as part of the model ID.

```bash
curl http://localhost:18080/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "geminicli:gemini-2.5-pro", "messages": [{"role": "user", "content": "Hello"}]}'
```

## Plain model IDs and aliases

Without a recognized prefix, the whole value is looked up in the model registry. Registered IDs come from discovery and from `models:` lists in `config.yaml`, where each `alias` becomes a routable ID:

```yaml config.yaml
openai-compatibility:
  - name: "groq"
    base-url: "https://api.groq.com/openai/v1"
    api-key-entries:
      - api-key: "YOUR_GROQ_KEY"
    models:
      - name: "openai/gpt-oss-20b"     # upstream model name
        alias: "groq:gpt-oss-20b"      # what clients send
```

When several providers serve the same ID, all of them are candidates and requests are spread across credentials according to `routing.strategy` (`round-robin` by default, or `fill-first`). Failures fail over to the next candidate.

Hidden aliases (`expose: false` or `visibility: private`) route normally but are left out of `GET /v1/models`.

## Credential prefixes (`prefix:` in config)

Provider credential entries (`gemini-api-key`, `claude-api-key`, `codex-api-key`, `openai-compatibility`, ...) accept a `prefix` field. Their models are then also registered as `<prefix>/<model>`:

```yaml config.yaml
gemini-api-key:
  - api-key: "YOUR_GEMINI_KEY"
    prefix: "team-a"      # also routable as "team-a/gemini-2.5-pro"
```

- The `prefix/model` IDs are hidden from `GET /v1/models` but always routable.
- With `force-model-prefix: true`, credentials that have a prefix register **only** the prefixed IDs, so unprefixed requests never use them.

This slash form is unrelated to the colon prefixes above.

## Virtual models

`virtual-models:` defines public model names backed by a weighted pool of provider/model members, with capability filtering. Examples are text-only members versus image input, and tool-replay safety.

```yaml config.yaml
virtual-models:
  ail-compound:
    expose: true
    strategy: weighted-round-robin
    fallback: true
    response_model: requested   # rewrite "model" in responses to "ail-compound"
    members:
      - id: m1
        provider: ollama
        model: llama3.2
        weight: 1
        capabilities: {operations: [chat], input: [text], output: [text]}
```

If no enabled member supports what the request needs, the response is `422` with `code: "no_eligible_backend"`.

## Thinking and reasoning suffixes

A parenthesized suffix on any model is removed before routing and turned into metadata:

- `gemini-2.5-pro(8192)` sets a thinking budget of 8192.
- `claude-sonnet-4-5(high)` sets the reasoning effort to `high`.

Providers that support thinking apply it; others ignore it.

## Checking what you can route to

```bash
curl http://localhost:18080/v1/models    -H "Authorization: Bearer YOUR_API_KEY"   # public model IDs
curl http://localhost:18080/v1/providers -H "Authorization: Bearer YOUR_API_KEY"   # providers with all their IDs
```
