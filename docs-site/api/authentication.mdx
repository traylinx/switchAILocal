switchAILocal has two independent credentials:

| Credential | Protects | Configured in |
|---|---|---|
| **Client API keys** | `/v1/*`, `/openai/v1/*`, `/v1beta/*`, `/v1/ws` (when `ws-auth: true`), Amp routes | `api-keys:` in `config.yaml` |
| **Management key** | `/v0/management/*` | `remote-management.secret-key` or `MANAGEMENT_PASSWORD` |

Provider credentials (Gemini, Claude, OpenAI-compatible keys, OAuth files) are a third, separate thing: they are what the gateway uses to call upstream providers and are never sent by clients.

## Configuring client API keys

Client keys are a top-level list of strings:

```yaml config.yaml
api-keys:
  - "sk-local-REPLACE-ME"
  - "sk-laptop-2-REPLACE-ME"
```

Keys can also be managed at runtime with the [Management API](/api/management/providers#client-api-keys) (`/v0/management/api-keys`). Changes are hot-reloaded.

There are no per-key names, scopes, permissions, or enable flags. A key either matches or it does not.

<Warning>
**If `api-keys` is empty, every request is accepted**, with or without a key. Combined with the default `host: ""` (all interfaces), that exposes your providers to the network. Always configure at least one key, or bind to `127.0.0.1`.
</Warning>

Generate a key with enough entropy, for example:

```bash
echo "sk-$(openssl rand -hex 24)"
```

## Sending the key

The gateway checks these locations in order and accepts the first one that matches a configured key:

| Location | Example |
|---|---|
| `Authorization` header | `Authorization: Bearer sk-local-REPLACE-ME` (a bare value without `Bearer ` also works) |
| `X-Goog-Api-Key` header | Gemini SDKs |
| `X-Api-Key` header | Anthropic SDKs |
| `key` query parameter | `/v1beta/models?key=sk-local-REPLACE-ME` |
| `auth_token` query parameter | `/v1/ws?auth_token=sk-local-REPLACE-ME` |

```bash
curl http://localhost:18080/v1/models \
  -H "Authorization: Bearer sk-local-REPLACE-ME"
```

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:18080/v1", api_key="sk-local-REPLACE-ME")
```

```python
import anthropic

client = anthropic.Anthropic(base_url="http://localhost:18080", api_key="sk-local-REPLACE-ME")
```

Prefer headers over query parameters: query strings end up in logs and browser history.

## Failure responses

| Status | Body | Cause |
|---|---|---|
| `401` | `{"error":"Missing API key"}` | Keys are configured and none of the locations above carried a value |
| `401` | `{"error":"Invalid API key"}` | A value was sent but matches no configured key |

## Routes that never require a client key

| Route | Notes |
|---|---|
| `GET /`, `GET /health` | Liveness information only |
| `GET /metrics` | Only exists when `observability.metrics.enabled: true`. Contains model and provider names; firewall it if exposed |
| `GET /management`, `GET /management.html` | Static control-panel page; the API calls it makes still need the management key |
| `GET /{anthropic,codex,google,iflow,antigravity}/callback` | OAuth browser redirects; they only accept a `state` that matches a pending login |
| `POST /v1internal:{method}` | Rejected with `403` unless the TCP peer is `127.0.0.1` |
| `GET /keep-alive` | Only registered by embedders that enable it; checks the local password instead |

See [Health & System](/api/system).

## WebSocket

`GET /v1/ws` uses the same API-key check when `ws-auth: true` (the default). Browsers cannot set headers on a WebSocket handshake, so pass the key as `?auth_token=` or `?key=`:

```javascript
const ws = new WebSocket("ws://localhost:18080/v1/ws?auth_token=sk-local-REPLACE-ME");
```

Setting `ws-auth: false` lets anyone who can reach the port register as a relay provider. The server logs a security warning at startup when it is off. Turning it back on (in the file or via `PUT /v0/management/ws-auth`) disconnects existing sessions.

## Management authentication

Management routes (`/v0/management/*`) do **not** accept client API keys. They take the management key in either header:

```bash
curl http://localhost:18080/v0/management/config \
  -H "Authorization: Bearer YOUR_MANAGEMENT_KEY"
# or
curl http://localhost:18080/v0/management/config \
  -H "X-Management-Key: YOUR_MANAGEMENT_KEY"
```

The key, remote access rules, the localhost behaviour when no key is set, and the brute-force ban are described in [Management API](/api/management/overview#authentication).

## Hardening checklist

- Configure `api-keys`; an empty list means open access.
- Bind to `127.0.0.1` unless other machines must reach the gateway.
- Keep `ws-auth: true`.
- Keep `remote-management.allow-remote: false` unless you need it, and never expose `/v0/management` to the internet.
- Put TLS in front (`tls.enable`, or a reverse proxy) if traffic leaves the machine.
- Enable `performance.rate-limiter` if the gateway is shared.
