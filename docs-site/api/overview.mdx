switchAILocal is a local gateway. It exposes OpenAI-, Anthropic-, and Gemini-compatible HTTP surfaces on one port and routes each request to a configured provider (CLI tools, local servers such as Ollama, or cloud APIs).

## Base URL

The server listens on `host:port` from `config.yaml` (the example config uses port `18080`). All examples in this reference assume:

```text
http://localhost:18080
```

<Warning>
The default `host` is `""`, which binds **all interfaces**. Set `host: "127.0.0.1"` if the gateway should only be reachable from your machine. See [Authentication](/api/authentication).
</Warning>

HTTPS is available by setting `tls.enable: true` with `tls.cert` and `tls.key`.

The standalone server registers no other routes; any path not listed returns `404`. Applications embedding the Go SDK can add routes with `WithRouterConfigurator`.

### Strict OpenAI namespace (`/openai/v1`)

`/openai/v1` is an additive alias group for third-party OpenAI clients. It uses the same handlers and auth as `/v1`:

| Route | Same as |
|---|---|
| `GET /openai/v1/models` | `GET /v1/models` |
| `POST /openai/v1/chat/completions` | `POST /v1/chat/completions` |
| `POST /openai/v1/completions` | `POST /v1/completions` |
| `POST /openai/v1/embeddings` | `POST /v1/embeddings` |
| `POST /openai/v1/images/generations` | `POST /v1/images/generations`, but the response is normalized to `data[]` |
| `POST /openai/v1/images/edits` | `POST /v1/images/edits`, but the response is normalized to `data[]` |

Only the two image routes behave differently; see [Images](/api/images#strict-openai-response-shape). Audio, music, responses, and messages routes have no `/openai/v1` alias.

## Quick example

```bash
curl http://localhost:18080/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "ollama:llama3.2",
    "messages": [{"role": "user", "content": "Hello!"}]
  }'
```

Any OpenAI SDK works by pointing `base_url` at `http://localhost:18080/v1`.

## Choosing a model

The `model` field decides where a request goes. You can send a plain model ID, an explicit `provider:model` prefix, a configured alias, a virtual model (for example `ail-compound`), or `auto` / `auto:<intent>`. See [Provider Prefixes](/api/provider-prefixes) and [Auto-Routing](/api/auto-routing).

## Common request headers

| Header | Used by | Meaning |
|---|---|---|
| `Authorization: Bearer <key>` | all API-key routes | Client API key (alternatives: `X-Api-Key`, `X-Goog-Api-Key`, `?key=`, `?auth_token=`) |
| `Idempotency-Key` | inference routes | Forwarded to the executor as request metadata; a UUID is generated when absent |
| `X-Ail-Autoinject: off` | `/v1/chat/completions` | Disables server-side `web_search` tool injection for this request |
| `X-Telegram-Bot-Token` | notifications | Per-request Telegram bot token |

## Common response headers

| Header | When |
|---|---|
| `X-Ail-Build` | Every `/v1/chat/completions` response: `<commit>-<hostname>` |
| `X-Auto-Routed: true`, `X-Selected-Model`, `X-Selected-Provider` | The request was resolved by the auto-routing engine |
| `X-Matched-Skill` | Chat completions, when intelligence skill matching selected a skill |
| `Retry-After` | `429` from the rate limiter or `503` from load shedding |
| `Access-Control-Allow-Origin: *` | All routes except the Amp management proxy; `OPTIONS` preflight returns `204` |

## Errors

### Authentication errors

The auth middleware answers before any handler runs, with a plain string body:

| Status | Body |
|---|---|
| `401` | `{"error":"Missing API key"}` |
| `401` | `{"error":"Invalid API key"}` |
| `500` | `{"error":"Authentication service error"}` |

### Handler errors

Inference handlers return an OpenAI-style envelope:

```json
{"error": {"message": "unknown provider for model foo", "type": "invalid_request_error"}}
```

`type` and `code` are derived from the status:

| Status | `type` | `code` |
|---|---|---|
| `400` and other 4xx | `invalid_request_error` | (none) |
| `401` | `authentication_error` | `invalid_api_key` |
| `403` | `permission_error` | `insufficient_quota` |
| `404` | `invalid_request_error` | `model_not_found` |
| `422` | `invalid_request_error` | `no_eligible_backend` (when no virtual-model member can serve the request) |
| `429` | `rate_limit_error` | `rate_limit_exceeded` |
| `5xx` | `server_error` | `internal_server_error` |

If the upstream provider's error text is itself valid JSON, it is returned verbatim instead of being wrapped.

Statuses you will commonly see:

| Status | Cause |
|---|---|
| `400` | `unknown provider for model <id>` (no provider serves that ID), unknown `provider:` prefix, or a missing required field |
| `501` | The chosen provider does not implement the operation (for example music on a non-MiniMax provider) |
| `503` | Explicit prefix for an API provider with no active credentials, or every candidate provider is open in the circuit breaker |
| `429` / `503` | `performance.rate-limiter` / `performance.load-shedding` rejected the request (with `Retry-After`) |

The [Anthropic Messages](/api/messages), [Gemini](/api/gemini), and [Notifications](/api/notifications) pages describe their own error shapes.

## Streaming

Streaming routes use Server-Sent Events (`text/event-stream`). The gateway waits for the first upstream chunk before committing to a `200`: an upstream failure before that point returns a normal JSON error with the real status code. A failure after streaming has started is written into the stream (see each endpoint), then the stream closes.

SSE keep-alive comments (`: keep-alive`) are sent every `streaming.keepalive-seconds` seconds; the built-in default is `0` (off). `streaming.bootstrap-retries` controls how many times a stream may be retried on another credential before the first byte (default `0`).
