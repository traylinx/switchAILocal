## Overview

switchAILocal can spread and fail over traffic at three levels. Pick the lowest level that solves your problem; each one is configured in `config.yaml` and needs no client changes.

| Level | You configure | switchAILocal does |
|-------|---------------|--------------------|
| Credentials of one provider | Several keys or logins for the same provider | Rotates (`round-robin` / `fill-first`), parks failing keys in cooldown, tries the next key |
| Providers that share a model ID | The same alias on several providers | Rotates the starting provider, fails over on retryable errors |
| Virtual model | A named pool of `provider` + `model` members | Weighted selection by request capability, optional one-shot fallback |

The last sections show patterns that stay in your client code (tiered waterfall, privacy routing, A/B tests). Details on cooldowns and error classes are in [Failover](/advanced/failover).

## 1. Several keys for one provider

```yaml config.yaml
gemini-api-key:
  - api-key: "YOUR_GEMINI_KEY_1"
  - api-key: "YOUR_GEMINI_KEY_2"

openai-compatibility:
  - name: "groq"
    base-url: "https://api.groq.com/openai/v1"
    api-key-entries:
      - api-key: "YOUR_GROQ_KEY_1"
      - api-key: "YOUR_GROQ_KEY_2"
    models:
      - name: "llama-3.3-70b-versatile"
        alias: "llama-70b"

routing:
  strategy: "round-robin"   # or "fill-first": use the first key until it cools down
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:18080/v1", api_key="sk-test-123")

for i in range(4):
    client.chat.completions.create(model="llama-70b", messages=[{"role": "user", "content": f"ping {i}"}])
```

Requests alternate between the two Groq keys. A key that returns 429 is skipped until its `Retry-After` (or exponential backoff) expires; within one request the other key is tried immediately. `routing.strategy` is hot-reloaded.

## 2. One model ID, several providers

If two providers register the same model ID, both serve it:

```yaml config.yaml
openai-compatibility:
  - name: "deepseek"
    base-url: "https://api.deepseek.com/v1"
    api-key-entries:
      - api-key: "YOUR_DEEPSEEK_KEY"
    models:
      - name: "deepseek-chat"
        alias: "fast"
  - name: "groq"
    base-url: "https://api.groq.com/openai/v1"
    api-key-entries:
      - api-key: "YOUR_GROQ_KEY"
    models:
      - name: "llama-3.3-70b-versatile"
        alias: "fast"
```

```bash
curl http://localhost:18080/v1/chat/completions \
  -H "Authorization: Bearer sk-test-123" -H "Content-Type: application/json" \
  -d '{"model": "fast", "messages": [{"role": "user", "content": "One-line summary of TCP"}]}'
```

- The starting provider rotates per request.
- On 5xx, 408, 429, 401/403, 402, timeouts or a pre-first-byte stream stall, the next provider is tried. Other 400/404/422 errors are returned unchanged.
- An explicit prefix (`ollama:llama3.2`) pins a request to one provider, so no failover happens.

## 3. Weighted pool with a virtual model

Use a [virtual model](/advanced/virtual-models) when you want a stable public name, explicit traffic shares, and capability-aware routing (for example only some members support tools or images):

```yaml config.yaml
virtual-models:
  team-chat:
    expose: true
    fallback: true                # one retry on another member for 402/408/429/5xx
    members:
      - id: groq-llama
        provider: groq
        model: llama-3.3-70b-versatile
        weight: 3
        capabilities:
          operations: [chat, chat_text_tools]
          input: [text]
          tools: true
      - id: local-llama
        provider: ollama
        model: llama3.2
        weight: 1
        capabilities:
          operations: [chat]
          input: [text]
```

```python
resp = client.chat.completions.create(model="team-chat", messages=[{"role": "user", "content": "Hi"}])
print(resp.model)  # always "team-chat"
```

Plain chat goes 3:1 between Groq and Ollama; requests with `tools` only go to `groq-llama`. If no member fits, the request fails with `422 no_eligible_backend`.

## 4. Let switchAILocal choose: auto-routing

`model: "auto"` (or `auto:coding`, `auto:fast`, ...) scores the available models on availability, quota, latency and success rate and returns a winner plus fallbacks. The response carries `X-Auto-Routed`, `X-Selected-Model` and `X-Selected-Provider` headers. See [Intelligent routing](/examples/intelligent-routing).

## Client-side patterns

These patterns are application logic. They are useful when the decision depends on your own business rules.

### Tiered waterfall (local first, then cloud)

```python
from openai import APIStatusError, APIConnectionError

TIERS = ["ollama:llama3.2", "fast", "sonnet"]   # local, cheap cloud alias, premium alias

def ask(prompt: str) -> str:
    last = None
    for model in TIERS:
        try:
            r = client.chat.completions.create(
                model=model,
                messages=[{"role": "user", "content": prompt}],
                timeout=30,
            )
            return r.choices[0].message.content
        except (APIStatusError, APIConnectionError) as e:
            last = e
    raise last
```

<Tip>
If you always want the same order, a virtual model with `fallback: true` or a shared alias (pattern 2) does this server-side with less code. A client-side waterfall is still useful when tiers differ in cost and you want strict priority instead of rotation.
</Tip>

### Privacy-aware routing

Keep sensitive prompts on the local machine:

```python
import re

SENSITIVE = [
    re.compile(r"\b\d{3}-\d{2}-\d{4}\b"),                       # US SSN
    re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.]+\b"),                  # e-mail
    re.compile(r"(?i)\b(password|api[_-]?key|secret)\b"),
]

def route(prompt: str) -> str:
    return "ollama:llama3.2" if any(p.search(prompt) for p in SENSITIVE) else "team-chat"

prompt = "My e-mail is jane@example.com, draft a reply to my landlord"
client.chat.completions.create(model=route(prompt), messages=[{"role": "user", "content": prompt}])
```

The Cortex Router plugin has a similar built-in rule: with `model: "auto"` it sends prompts containing an e-mail address to the `secure` slot of `intelligence.matrix`. For redaction instead of rerouting, see the Lua privacy-firewall example in the repository (`examples/middleware/privacy-firewall`) and [Lua plugins](/advanced/lua-plugins).

### A/B comparison

```python
import time

def compare(models, prompt, runs=3):
    for model in models:
        times = []
        for _ in range(runs):
            t = time.perf_counter()
            client.chat.completions.create(model=model, messages=[{"role": "user", "content": prompt}], max_tokens=200)
            times.append(time.perf_counter() - t)
        print(f"{model:24s} avg {sum(times)/len(times):.2f}s")

compare(["ollama:llama3.2", "llama-70b", "sonnet"], "Explain recursion in two sentences.")
```

For production traffic splits use weights in a virtual model instead.

### Consensus across providers

```python
from collections import Counter

def consensus(question: str, models=("ollama:llama3.2", "llama-70b", "sonnet")) -> str:
    answers = []
    for m in models:
        r = client.chat.completions.create(
            model=m,
            messages=[{"role": "user", "content": question + " Answer with one word."}],
            temperature=0,
        )
        answers.append(r.choices[0].message.content.strip().lower())
    return Counter(answers).most_common(1)[0][0]
```


## Defaults and limits

| Behaviour | Default |
|-----------|---------|
| Credential selection | `round-robin` |
| Cooldown-wait retry rounds | off until `max-retry-interval` > 0 (`request-retry` sets the round count) |
| Circuit breaker | per provider; see `performance.circuit-breaker` |
| Virtual-model fallback | off; at most one extra member when `fallback: true` |
| Streams | failover only before the first chunk is sent |

## Troubleshooting

<AccordionGroup>
  <Accordion title="Traffic never reaches the second key">
    With `fill-first`, the second key is only used while the first is cooling down. Switch to `round-robin` for even spread.
  </Accordion>
  <Accordion title="No failover between two providers">
    Both must register the **same** model ID. Check that the alias strings match exactly, and that you did not use a provider prefix in the request.
  </Accordion>
  <Accordion title="429 model_cooldown">
    All credentials for that model are cooling down. Add credentials, add another provider with the same alias, or wait for `Retry-After`.
  </Accordion>
  <Accordion title="422 no_eligible_backend from a virtual model">
    No member declares the capability this request needs (tools, images, tool history). See [Virtual models](/advanced/virtual-models).
  </Accordion>
</AccordionGroup>
